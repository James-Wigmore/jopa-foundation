# JOPA Foundation Uganda — Website

Static, multi-page site for JOPA Foundation Uganda. Deployed as plain
static files — no framework, no bundler. As of this update there IS a
small build step (see below), but it's one dependency-free Node script,
not a framework.

## What changed: navbar/footer are now injected at build time

Previously every page had `<div id="navbar"></div>` / `<div
id="footer"></div>`, and `js/include.js` used `fetch()` in the browser
to pull in `components/navbar.html` and `components/footer.html` at
runtime. That caused a few real problems: a brief flash of missing
nav/footer on every page load, a network request the page couldn't
render without, search crawlers seeing an empty nav/footer if they
don't run JS, and the "active" nav link being figured out client-side.

`build.js` now does that same injection once, at build time, directly
into plain HTML — so what actually deploys already has the real
nav/footer baked in, with the current page's nav link already marked
active before the browser sees anything.

## Making a change — the new workflow

1. Edit the page in **`src/pages/`**, not the root `.html` file. The
   root files are generated output; editing them directly means your
   change gets silently overwritten the next time someone runs the
   build.
2. Editing the navbar or footer itself? Edit **`components/navbar.html`**
   or **`components/footer.html`** — same as before, nothing moved.
3. Run the build:
   ```
   node build.js
   ```
4. Commit **both** your `src/` (or `components/`) change AND the
   regenerated root `.html` files. The root files are what Vercel
   actually serves — if you only commit the source and forget to
   run the build (or forget to commit its output), the live site
   won't reflect your change at all.
5. Push to `develop` as usual. No Vercel build-command changes needed
   — the output is the same flat static HTML Vercel already expects.

**Adding a new page?** Add it to `src/pages/`, add its nav link to
`components/navbar.html`, and add its filename → URL slug mapping to
the `SLUG_BY_FILE` object near the top of `build.js` — otherwise the
build script will skip it with a warning.

## Running locally

Any static file server works. If using VS Code's Live Server
extension, make sure the folder you open is this project's **root**
(the one containing the built `index.html`), not `src/` — otherwise
relative asset paths resolve differently than they do in production.
Since `include.js` no longer fetches anything, you technically *can*
open the built `index.html` directly by double-clicking it now — but
Live Server is still recommended for a realistic preview.

## Forms (Formspree)

Unchanged from before — all forms are handled by one shared handler
in `js/script.js`, routed by a `FORMSPREE_IDS` lookup table near the
top of that file. See the comments in that file for how to update or
add a form ID.

## Deployment

Deployed via Vercel from the `develop` branch, with `vercel.json`
enabling clean URLs (`/about` instead of `/about.html`). After pushing
changes, hard-refresh (Ctrl+Shift+R / Cmd+Shift+R) before testing —
browsers can cache old CSS/JS and make a successful deploy look like
it didn't take effect.
